## RWF-165 — A module's lookup list changed through `process.mainModule.children`

**Status:** Open (backlog `BL-132`)
**Failure class:** false `NOT_AFFECTED`
**Defect class:** A (the analyzer recognises the module object reached
through `require.main.children`, `module.parent.children` and
`require.cache`, but not the same object reached through
`process.mainModule.children`)
**Proof family affected:** B (BL-092's setup)
**Severity:** P0 / a live false `NOT_AFFECTED`, pre-existing
**Fix lane:** C (the loader classifier's capability chains)

**Discovered:** by task BL-126's independent audit (round 1, B1), checking
that Node's module loader objects, which the widened trust boundary keeps
inside the claim (SOUNDNESS-CONTRACT § 1, "What it does not cover: Node's
module loader objects"), are analyzed as loader capabilities. On BL-126's
branch, whose analyzer rules are unchanged from its base `85195065` (only
disclosure strings differ), against
real Node v22.11.0, real Node calls the target and the analyzer answers
`NOT_AFFECTED`, family B
(`tests/oracle/bl126-main-module-children.cases.ts`, open-soundness-defect
records):

```js
// wrap/index.js, before `require("vuln-lib/index.js")`
process.mainModule.children[0].paths.shift();
```

`process.mainModule` is the entry's module object; its first child is
`wrap`'s own module object, so the `shift()` drops `wrap/node_modules`
from the list `wrap`'s `require` searches, and the affected top-level
`vuln-lib@1.0.0` loads instead of the decoy. The same through an alias
(`const c = process.mainModule.children; c[0].paths.shift();`) and by
replacing the list are cases too. The same change through
`require.main.children[0]` is `UNKNOWN` (`modeled.require-main-children`),
and the auditor measured `module.parent.children[0]…`,
`require.cache[__filename]…`, `require("module")._cache[…]…`,
`Object.values(require.cache)…` and
`process.mainModule.constructor._cache[…]…` as `UNKNOWN` too. Reading the
list without changing it keeps the proof, and real Node loads the decoy
(`control.main-module-children-read`).

**Not the trust boundary's.** The change is to a module object, a loader
object, which the boundary does not cover; a store onto
`process.mainModule` itself would change `process`, a built-in object.

**Related, not the same:** RWF-140 (`process` handed on or wrapped, so
`process.mainModule` is not recognised; here `process` is spelled) and
RWF-065 (`module.children[i].require`, family A).

**Not measured:** other releases than v22.11.0; `children` reached from a
module object other than the main module's (`module.children` is
`require.main.children` here).
