## RWF-163 — Replacing a member of `require("path")` or `require("fs")` redirects Node's loader

**Status:** Open (backlog `BL-122`)
**Failure class:** false `NOT_AFFECTED`
**Defect class:** B (the analyzer takes Node's loader to resolve and read
files with Node's own `path` and `fs` functions; a loaded file may have
replaced them on the shared exports objects)
**Proof family affected:** B (BL-092's setup)
**Severity:** P0 / a live false `NOT_AFFECTED`, pre-existing
**Fix lane:** C (a closure-wide rule over stores onto a builtin module's
exports object), or the trust boundary, by the project owner's decision

**Discovered:** by task BL-122, inventorying which builtin objects outside
the ECMAScript intrinsic prototypes Node's loader touches after startup
(`scripts/bl122-trust-boundary-reach/probe-reach.cjs`). On the base
`58a5f32`, against real Node v22.11.0, real Node calls the target and the
analyzer answers `NOT_AFFECTED`, family B, in ten forms
(`tests/oracle/bl122-trust-boundary-reach.cases.ts`, `o3.*`, each an
open-soundness-defect record; its controls `control.o3-*`, an identity
wrapper on the same member, keep their proof and real Node does not call
the target):

```js
// wrap/index.js, before `require("vuln-lib/index.js")` -- no loader construct
const __m = require("path");
const __o = __m.resolve;
__m.resolve = function (...a) {
  const r = __o.apply(this, a);
  return typeof r === "string" ? r.replace("/wrap/node_modules/vuln-lib", "/vuln-lib") : r;
};
```

The forms: `path.resolve` assigned, redefined with `Object.defineProperty`
on `require("node:path")`, assigned through `require("path/posix")` (the
same object on POSIX), assigned by a sibling module loaded first, and
assigned before `require()` of an ES module (below); `fs.realpathSync`
assigned, set through `Reflect.set`, and assigned by a function handed
`require("fs")` as a parameter (graceful-fs's shape, which a rule over
spelled receivers misses); and `fs.readFileSync` assigned, which makes the
decoy run the affected instance's source under the decoy's own module
identity, rather than load the affected instance; and `fs.openSync`
replaced before `require()` of an ES module (below).

**The mechanism.** `internal/modules/cjs/loader.js` and
`internal/modules/helpers.js` hold `const fs = require('fs')` and
`const path = require('path')` and call members on them at each load
(helpers.js: "Import all of `fs` so that it can be monkey-patched"):
`path.resolve` builds every candidate path in `Module._findPath`,
`toRealPath` calls `fs.realpathSync` on the file found, and the `.js` and
`.json` handlers read the source with `fs.readFileSync`. A program's
`require("path")` returns that same exports object, so a replaced member
runs inside the loader. The inventory finds the same members called on
every release installed, v20.19.0 to v26.12.1, and also `path.dirname`,
`join`, `normalize`, `basename`, `isAbsolute`, `toNamespacedPath` and the
reads of `path.posix` and `path.sep` (up to v24.12.0).

**Why it is not the boundary's case.** SOUNDNESS-CONTRACT § 1's trust
boundary covers the ECMAScript intrinsic prototypes; a builtin module's
exports object is listed among what it does not cover ("a builtin
module's exports object, such as `fs`'s"), and ADR 0010's decision record
leaves the reach to the project owner (backlog `BL-122`). The result's
scope disclosure also names "loader monkey-patching originating in code
this scan never analyzed" as an exclusion, which implies the analyzer
models loader monkey-patching in code it did analyze; for these members
it does not.

**The ES module resolver too.** `internal/modules/esm/resolve`
destructures `realpathSync` and `resolve` from `fs` and `path` when it
loads, and it loads lazily: a CommonJS program that replaces one of them
before its first ES module load hands the resolver the replacement for
good. `o3.path-resolve-require-esm` replaces `path.resolve`, `require()`s
an ES module that imports `vuln-lib/index.js`, and restores it: real Node
calls the target on v20.19.0 to v26.12.1 (every release measured where
`require()` of an ES module runs; it throws on v22.11.0), and the analyzer
answers `NOT_AFFECTED`, family B
(`scripts/bl122-trust-boundary-reach/require-esm-route.mjs`; the oracle
asserts the release's ground truth from `node-release-routes.ts`,
`require-esm-resolver`). Found by BL-122's independent audit (round 1),
which corrected this record's first statement that a later replacement
does not reach the ES module loader.

The ES module loader also reads the module's source with
`readFileSync(url)` and no encoding, which opens the file through
`fs.openSync`, `fs.readSync` and `fs.closeSync` on the shared `fs`
exports object. `o3.fs-opensync-require-esm` replaces `fs.openSync` to
open the affected instance's file for the decoy's URL: real Node calls
the target on the same releases, and the analyzer answers `NOT_AFFECTED`,
family B. Found by BL-122's independent audit (round 2). The members a
`require()` of an ES module touches are inventoried in
`scripts/bl122-trust-boundary-reach/reach-releases.md`; only these two
forms were tried end to end.

**Not measured:** `require.resolve` and `module.createRequire` routes,
which use the same functions; `fs.realpathSync` before `require()` of an
ES module throws on v26.0.0 and calls the target on every other release
measured, so only the `path.resolve` form is a case.
