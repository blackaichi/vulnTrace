## RWF-161 — A species defined on the `Array` constructor reaches Node's loader outside the trust boundary

**Status:** Open (backlog `BL-122`)
**Failure class:** false `NOT_AFFECTED`
**Defect class:** B (the analyzer takes Node's loader to build its lookup
arrays as plain arrays; a module may have changed the species the
loader's own `slice` honours)
**Proof family affected:** B (BL-092's setup)
**Severity:** P1 / a live false `NOT_AFFECTED`, pre-existing
**Fix lane:** C, with lane A's builtin-store facts (a closure-wide fact,
as RWF-156), or the trust boundary, by the project owner's decision

**Discovered:** by task BL-113, checking whether the trust boundary as
the project owner worded it ("no loaded file changes Node's builtin
prototypes", ADR 0010, "Decision record — BL-111") covers RWF-156's
class. On the base `03449a1`, against real Node v22.11.0, real Node calls
the target and the analyzer answers `NOT_AFFECTED`, family B
(`tests/oracle/bl113-trust-boundary.cases.ts`,
`outside.array-species-own`, an open-soundness-defect record):

```js
// wrap/index.js, before `require("vuln-lib/index.js")` -- no use of module.paths
Object.defineProperty(Array, Symbol.species, {
  configurable: true,
  get() {
    return function () {
      return new Proxy([], { set(t, k, v) {
        if (typeof v === "string" && v.endsWith("/wrap/node_modules")) v = "/nonexistent";
        t[k] = v; return true;
      } });
    };
  },
});
```

**The mechanism.** RWF-156's `audit3.species-constructor-store` reaches
the species through `Array.prototype.constructor`, a built-in prototype's
property, which the trust boundary (SOUNDNESS-CONTRACT § 1) now covers.
`ArraySpeciesCreate` reads the receiver's `constructor` and then that
constructor's `Symbol.species`. That second read is an own accessor of the
`Array` constructor, so redefining it changes no prototype: the loader's
`ArrayPrototypeSlice` of the lookup paths (`Module._resolveLookupPaths`)
builds the array the getter returns, and the loader's `unshift` writes
`wrap`'s directories into it. The analyzer's escape row sees the define
call (its getter gets a `possible` edge), but nothing the program calls
reaches the target: the loader does, by loading another instance.

**Why it is not the boundary's case.** The decision record leaves the
boundary's reach beyond builtin prototypes undecided, naming "a builtin
constructor's own properties" among the objects it may or may not cover.
Task BL-113 worded the boundary over the ECMAScript intrinsic prototypes
only, so this route is an open defect until the project owner decides
the reach (backlog `BL-122`): either the boundary covers a constructor's
own properties (this record then moves to the documented limitation), or
the analyzer must withdraw the closure on such a store (a closure-wide
rule, as option (B) was).

**Not measured:** other releases than v22.11.0 (the route uses the same
`slice` as `audit3.species-constructor-store`, which CI's Node 20 and 26
run). The class is "a constructor's own `Symbol.species`": `Promise`,
`RegExp`, `ArrayBuffer`, `%TypedArray%`, `Map` and `Set` have an own,
configurable `Symbol.species` accessor as well (BL-113's independent
audit). Whether Node's loader honours any of them on a route the
analyzer calls complete is not measured; `Promise` (the ES module
loader's `PromisePrototypeThen`, through `require()` of an ES module on
v22.12 and later) and `%TypedArray%` / `ArrayBuffer` (`Buffer` slices)
first.
