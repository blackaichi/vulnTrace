# RWB-08 — debug → ms (nested/transitive dependency instance; `OTHER` in the reachability-pattern vocabulary)

Real-world benchmark case, design: `docs/REAL-WORLD-BENCHMARK-V0.1.md § RWB-08`.

- **Package installed directly:** `debug@2.0.0`; **actual vulnerable package (transitive):** `ms@0.6.2`
- **Advisory:** GHSA-3fx5-fwvr-xrjg / CVE-2015-8315 (ReDoS, CWE-1333/400) — re-verified live at fixture-creation time via `https://api.osv.dev/v1/vulns/GHSA-3fx5-fwvr-xrjg`, unchanged from the design doc
- **Vulnerable versions:** `ms <0.7.1`
- **Patched versions:** `ms >=0.7.1`
- **Vulnerable symbol:** `ms`'s default exported function (its string-parsing regex). Reached **indirectly**: real installed `node_modules/debug/debug.js:14`: `exports.humanize = require('ms');` — `debug` re-exports `ms`'s entire `module.exports` function verbatim as `debug.humanize`.
- **Design-doc correction applied here:** the design doc's original snippet (`require("debug")("app:limits").humanize(...)`) does not actually work — verified live: the per-namespace logger function `debug('app:limits')` returns does **not** have `.humanize` copied onto it (confirmed by reading `debug.js`'s `debug()` factory function, and by a direct `node -e` reproduction that threw `TypeError: debug.humanize is not a function`). The real, working call is `require('debug').humanize(...)` — directly on the module's own top-level export, which **does** carry `.humanize` (verified: `require('debug').humanize('2 days')` → `172800000`). The fixture below uses this corrected, verified-working shape.
- **Application entrypoint:** `src/rate-limit.js`
- **Expected verdict:** `AFFECTED`
- **Expected reachable path:** `src/rate-limit.js` `parseWindow()` → `debug.humanize(...)` (a property access on the `debug` module's own exports — no `require('ms')` anywhere in application code) → resolves, via `debug`'s own `exports.humanize = require('ms')` re-export, to `ms`'s real default-export function in `node_modules/ms/index.js` (hoisted to top-level `node_modules/ms/` by npm in this fixture's real resolution).
- **Why this is the hardest case in the set:** the finding must be attributed to package `ms` at version `0.6.2` — not `debug` — while the application-side call site names only `debug.humanize`. `ms`'s own `lib/index.js`-equivalent (`index.js`) is never `require()`'d anywhere in `src/`; the only path to it is through a re-export inside a *different* package's own source. `src/code-intelligence/module-model.ts` documents that chasing a re-export to its ultimate source file is not attempted for the general case — whether VulnTrace's alias/call-graph machinery nonetheless resolves this specific pattern (a bare `exports.x = require(...)` re-export) is exactly what this case exists to observe; this document does not assume an outcome. See `tests/validation/FINDINGS.md` for the actual result.
- **Advisory source:** `https://api.osv.dev/v1/vulns/GHSA-3fx5-fwvr-xrjg`
- **Vulnerable source location:** real installed `debug@2.0.0`, `debug.js` line 14; real resolved `node_modules/ms/index.js` (version `0.6.2`, confirmed via `node_modules/ms/package.json`)
- **Reproducibility:** `package.json`/`package-lock.json` pin `debug@2.0.0`, which resolves `ms@0.6.2` transitively via a real `npm install` (confirmed live against the real registry tarballs). `node_modules/` is pruned to `debug/{node.js,debug.js,package.json}` and `ms/{index.js,package.json}` only, verified functionally equivalent via a direct `node -e` smoke test (`require('debug').humanize('2 days')` → `172800000`) after pruning.
