# RWB-10 — handlebars (UNKNOWN via unresolvable dynamic dispatch)

Real-world benchmark case, design: `docs/REAL-WORLD-BENCHMARK-V0.1.md § RWB-10`.

- **Package:** `handlebars@4.7.6`
- **Advisory:** GHSA-f2jv-r9rf-7988 / CVE-2021-23369 (RCE via template compilation, CWE-94) — re-verified live at fixture-creation time via `https://api.osv.dev/v1/vulns/GHSA-f2jv-r9rf-7988`, unchanged from the design doc
- **Vulnerable versions:** `<4.7.7`
- **Patched versions:** `>=4.7.7`
- **Vulnerable symbol:** the exported `compile(input, options, env)` function. Confirmed present at `lib/handlebars/compiler/compiler.js:510` (`export function compile(input, options = {}, env) {...}`) in the real installed source; the real `require('handlebars')` entry (`lib/index.js` → `dist/cjs/handlebars.js`) attaches it as `hb.compile = function (input, options) {...}` on a runtime-constructed object inside a `create()` factory (`dist/cjs/handlebars.js:38`) — a dynamic property assignment, not a static object literal, structurally similar to the UMD pattern behind `tests/validation/FINDINGS.md`'s `RWF-001`.
- **Live reproduction:** the real, working call chain was verified before writing the final fixture: `require('handlebars').compile('Hello {{name}}')({name:'World'})` → `"Hello World"`.
- **Application entrypoint:** `src/template-engine.js`
- **Expected verdict:** `UNKNOWN`
- **What exactly prevents a sound conclusion:** `renderTemplate()` builds a registry `{ hbs: Handlebars.compile, upper: upperCompile }` (a second, real, unrelated function — not a single-entry object that would trivially resolve to `Handlebars.compile` regardless of key), then reads `config.json`'s `templateEngine` value **at runtime** and looks it up as `engines[engineName]`. This is a computed property access keyed by a value VulnTrace cannot statically evaluate (it comes from parsing a JSON file at runtime, not a literal in the source). VulnTrace can see that `engines.hbs` is `Handlebars.compile` and that `compile(...)` is called, but it cannot soundly prove whether *this specific call site* ever actually binds `compile` to `Handlebars.compile` versus `upperCompile`.
- **Why UNKNOWN and not NOT_AFFECTED:** per `AGENTS.md`'s core rule, never infer `NOT_AFFECTED` merely because resolution failed — an unresolved dynamic-dispatch target must fall back to `UNKNOWN`. `config.json` in this fixture actually sets `"templateEngine": "hbs"` (i.e., the vulnerable branch genuinely *is* taken at runtime) specifically so that a false `NOT_AFFECTED` here would be the exact critical security failure `docs/VALIDATION-STRATEGY.md § 10` names — VulnTrace has no way to know this without evaluating the config file's contents, which is out of its static-analysis scope.
- **Why UNKNOWN and not AFFECTED:** VulnTrace must not guess that the dynamic key resolves to the vulnerable branch either — an application whose config instead set `"templateEngine": "upper"` would make the exact same source code correctly `NOT_AFFECTED`, so a confident `AFFECTED` verdict from static source alone would be an unproven guess in the general case.
- **Advisory source:** `https://api.osv.dev/v1/vulns/GHSA-f2jv-r9rf-7988`
- **Vulnerable source location:** real installed `handlebars@4.7.6`, `lib/handlebars/compiler/compiler.js:510`, `dist/cjs/handlebars.js:38`
- **Reproducibility:** `package.json`/`package-lock.json` pin the exact vulnerable version; `node_modules/handlebars/` itself is pruned (bin/, AMD/UMD bundles, docs, types dropped — 3.0 MB → 996 KB). `handlebars`'s real dependencies `uglify-js`/`source-map`/`neo-async`/`wordwrap`/`minimist` (used only by its `bin/precompiler.js` CLI, confirmed by grepping for their names across `dist/cjs/*.js` — only `precompiler.js` references them) are dropped entirely, since our fixture only ever calls `require('handlebars').compile()`, never the CLI. Total `node_modules/` ~972 KB. Verified functionally equivalent via the live reproduction above running against the fully pruned tree, both directly and through `src/template-engine.js` itself.
