# AGENTS.md — VulnTrace

Standing instructions for coding agents working on this repository. This
file is an **index and a workflow**, not a second copy of the
architecture: where a rule is already stated in an authoritative document,
this file names the document and section instead of restating it, so the
two cannot drift. If this file and the document it cites disagree, the
document wins and this file is the one to fix.

## A. Mission

VulnTrace is a **vulnerability reachability analyzer** for JavaScript and
TypeScript. Technically, it is a **proof-producing vulnerability triage
engine**. It is not a scanner. A scanner, SCA tool or SBOM feed finds
candidates. VulnTrace **adjudicates** one candidate vulnerability against
one exact installed `PackageInstance`, and answers `AFFECTED`,
`NOT_AFFECTED` or `UNKNOWN`, with evidence.

Full positioning: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) § 1.

## C. Documents are claims to verify, not facts

This project has caught its own records being wrong more than once:

- the OPEN-DEBTS § 3 criterion-3 assertion (see OPEN-DEBTS D-15);
- the scorecard's RWF status classifier, which could silently drop a row;
- a FINDINGS prose generalisation that was written from one reproduction
  without measuring the others (RWF-046a);
- a production comment's premise in
  `src/code-intelligence/named-bindings.ts` (RWF-046a), which was corrected
  by RWF-049's measurement, and then corrected again.

Before you rely on a documented claim for a soundness decision, verify it
against the code, and where it is about JavaScript semantics, against real
`node`. If the document is wrong, the correction is itself a finding.
Report it. Do not work around it silently.

## D. Premise verification

Before you act on any factual claim in a prompt or task file, verify it.
This covers claims about the code, about JavaScript semantics, and about
measured results.

If the claim is false:

- do the measured, correct thing;
- state the deviation plainly in the report (section J, item 8);
- **never implement a false premise because it was instructed.**

If the correct thing is unclear, or it falls outside the task's
boundaries, stop and report `NEEDS_DECISION` or `STOPPED_ON_FINDING`.

## E. Soundness rules

The rules themselves live in the authoritative documents. These are the
ones every change is checked against:

- **Priority order**: soundness > explainability > precision > coverage >
  performance. `UNKNOWN` is a first-class result. A false `NOT_AFFECTED`
  is the critical failure. When anything is not established, fail closed to
  `UNKNOWN`. See ARCHITECTURE § 2 and § 13.
- **Verdicts**: `AFFECTED` requires an authoritative target **and** a
  concrete reachable path. `NOT_AFFECTED` requires positive proof from
  **exactly one** negative-proof family (A, B or C). See
  SOUNDNESS-CONTRACT § 1, § 3 and § 4 (VT-CONTRACT-01/02/03). Adding a
  proof family is governed by SOUNDNESS-CONTRACT § 6.
- **Uncertainty**: there are exactly **six** uncertainty categories. Never
  add a seventh casually. A finer reason is a subtype within an existing
  category. See ARCHITECTURE § 6.1.
- **Identity**: exact `PackageInstance` identity is mandatory. The same
  name and version at different installed paths are different instances,
  and nothing compares, keys or reports by `name@version`. See ARCHITECTURE
  § 4. Target attribution binds to an exact instance (ARCHITECTURE § 7).
- **No execution**: target code is never executed, and target lifecycle
  scripts are never run.
- **Edges**: a fabricated call edge is a soundness defect even if no
  verdict moves. An edge withdrawn into `UNKNOWN` can be a correct
  soundness fix, even though it costs precision.
- **Performance** never becomes proof authority (ARCHITECTURE § 2 and
  § 9.1).

## F. The three recurring defect classes

Check every change against all three:

- **A. Wrong binding identity**: identifier *text* reaches an
  authoritative attribution. A local name is matched by spelling instead
  of by the binding it actually refers to (RWF-043, RWF-045, RWF-046,
  RWF-046a). `tests/binding-grammar/` sweeps this class.
- **B. Correct binding, wrong runtime-value semantics**: the binding is
  right, but the value the analyzer assumes it holds is not what real
  `node` produces.
- **C. Multi-valued provenance collapsed to one value**: a binding that
  can hold several values at runtime (reassignment, branches, deferred
  writes, parameters from many call sites) is treated as holding one.

Also see OPEN-DEBTS D-15: a remediation can introduce the class it was
closing.

## G. Testing rules

- **Failing first.** For a reproduced soundness bug, write the tests and
  show them failing on the base commit **before** the fix.
- **Loud fixtures.** Fixture packages export every name their cases bind.
  That way a fabricated attribution resolves loudly to a wrong target
  instead of degrading quietly to `UNKNOWN`.
- **Mutations attack the authority itself.** Each mutation must be caught
  by a named test. A `PackageInstance` mutation must show a **sibling
  borrow** (a sibling instance's code attributed to this instance), not
  merely a lost edge. See ARCHITECTURE § 13, rule 7.
- **Differentials are reported separately**: graph, proof and verdict. A
  zero corpus differential is **not** evidence of soundness. See
  OPEN-DEBTS D-12.
- **Never pin a wrong verdict** as a test's expected outcome. A known
  disagreement is recorded as a disagreement, with the correct answer left
  standing (for example, OPEN-DEBTS D-09 and `tests/binding-grammar/`).
- **Performance is tested structurally**: operation counts and index
  builds, not wall clock alone. Never relax a threshold to get green. See
  ARCHITECTURE § 10 and § 10.2.
- New Foundation invariants are registered in
  `src/testing/foundation-invariants.ts` (ARCHITECTURE § 10.1).

## H. Git workflow

- Before starting: `git fetch origin --prune`, fast-forward `main`, clean
  tree, `main` == `origin/main`. Record the base SHA.
- Branch from merged `main` only. Never stack on an unmerged branch.
- One conceptual task per branch. Make logical commits. If the task has a
  task file, it is the first commit (see
  [`docs/tasks/README.md`](docs/tasks/README.md)).
- The only allowed attribution trailer is:

  ```text
  Co-Authored-By: Claude <noreply@anthropic.com>
  ```

- Forbidden in commit metadata: model names, session IDs, `claude.ai`
  URLs, "generated by" lines, and any telemetry. Enforced by
  `npm run validate:metadata`. See ARCHITECTURE § 11.
- Push the branch. **Never create a PR. Never merge.** The user does both.
- Force-push only your own unmerged branch, and only when a rebase was
  instructed.
- Do not touch, unlock or remove another task's worktree.

## I. Gates

Every task runs the full set, unrelaxed:

| Gate | Command |
| --- | --- |
| full suite | `npm test` |
| Foundation gate | `npm run test:foundation` |
| adversarial suites | `npm run test:adversarial` |
| performance smoke | `npm run test:performance` |
| real-world validation | `npm run test:validation` |
| binding-form grammar sweep | `npm run test:binding-grammar` |
| typecheck | `npm run typecheck` |
| lint | `npm run lint` |
| prettier | `npm run format` |
| build | `npm run build` |
| history + commit metadata | `npm run validate:history` |
| commit metadata | `npm run validate:metadata` |
| scorecard freshness | `node scripts/generate-scorecard.mjs --check` |
| documentation references | `node scripts/check-docs.mjs` |

- Do not change thresholds, skip tests or edit configuration to get green.
- `npm test` and `npm run test:validation` use the network (OPEN-DEBTS
  D-03, ARCHITECTURE § 10). A network failure is reported as one. It is
  not a pass.
- `npm run test:validation` has documented known failures (OPEN-DEBTS
  D-09). Compare them case by case, verdict by verdict, against that
  baseline. Do not ignore them. A known failure that changes verdict, or
  a new failure, is a finding.

## J. Report format

Every task ends with a report in exactly this order:

1. **VERDICT**: `READY_FOR_PR` | `BLOCKED` | `STOPPED_ON_FINDING` |
   `NEEDS_DECISION`
2. **STATE**: base SHA, branch, HEAD SHA, tree clean, pushed, no PR, no
   merge
3. **WHAT CHANGED**: files touched; behaviour changed (or "none")
4. **EVIDENCE**: tests added (failing on base, passing after); mutations
   and the named test that caught each
5. **DIFFERENTIALS**: graph, proof and verdict, as numbers; validation
   against the documented known failures
6. **GATES**: each gate named, with its result
7. **ACCEPTANCE**: each acceptance criterion answered yes/no
8. **DEVIATIONS**: anything done differently from the task, and why
9. **NOT ACTED ON**: findings noticed and deliberately left alone
10. **UNRESOLVED**: what could not be established, and what would settle
    it

## K. Scope

Scope is set by the current phase and its open work, not by a fixed list:

- the current phase, its entry criteria and its direction:
  OPEN-DEBTS § 3 and § 4;
- every known debt: OPEN-DEBTS § 1;
- the measured state, including where the `UNKNOWN` pressure is and the
  RWF register: SCORECARD § 7 and § 8;
- the RWF records themselves: `tests/validation/FINDINGS.md`.

A task file narrows scope further. Do not add out-of-scope features just
because they seem useful. Do not pre-commit to a capability that the
evidence has not chosen (OPEN-DEBTS § 4).
